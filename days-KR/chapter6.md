# 6장: AI 테스트와 보안

## 강의 개요

> "소프트웨어 오류는 제품/회사에 대한 사용자의 신뢰를 무너뜨리고 막대한 금전적 비용을 초래할 수 있다"

LLM이 코드의 대부분을 작성한다면, 오류를 막기 위한 광범위한 가드레일이 필요합니다. AI 시대에 소프트웨어 품질은 그 어느 때보다 중요합니다.

### 학습 목표
- 전통적인 보안 위협과 테스트 방법 이해
- SAST, DAST, SCA 등 보안 테스트 기법 숙지
- 새로운 AI 에이전트 공격 벡터 이해
- 보안 테스트에서 LLM의 한계 학습

## 1. 전통적인 위협 지형

### OWASP Top 10 위협

| 위협 유형 | 설명 |
|-----------|------|
| SQL Injections | SQL 인젝션 공격 |
| Cross-site scripting (XSS) | 크로스 사이트 스크립팅 공격 |
| Broken authentication | 인증 체계 손상 |
| Insecure direct object references | 안전하지 않은 직접 객체 참조 |
| Security misconfigurations | 보안 설정 오류 |
| Sensitive data exposure | 민감 데이터 노출 |

## 2. 취약점 탐지 기법

### SAST (정적 애플리케이션 보안 테스트, Static Application Security Testing)
- **유형**: 화이트박스 테스트
- **분석 대상**: 바이너리와 소스 코드
- **단계**: SDLC 초기 (문제를 찾고 고치는 비용이 가장 저렴)
- **기법**: 코드베이스 패턴 매칭 스캔
- **발견 대상**: SQL 인젝션, 명령어 인젝션, 크로스 사이트 스크립팅

### DAST (동적 애플리케이션 보안 테스트, Dynamic Application Security Testing)
- **유형**: 블랙박스 테스트
- **방법**: 실제 해커를 흉내 내어 취약점 발견
- **단계**: SDLC 전반, 오탐이 적음
- **기법**:
  - 입력 퍼징(fuzzing)
  - 세션 토큰 조작
  - 설정/헤더 테스트
  - 무차별 대입(brute force) 속도 제한 테스트

### SCA (소프트웨어 구성 분석, Software Composition Analysis)
- **분석 대상**: 애플리케이션이 사용하는 오픈소스 패키지를 심층 분석
- **방법**: 패키지 매니저, IaC(Infrastructure as Code), 풀(pull)한 이미지 분석
- **기법**: 의존성 취약점 스캔

### 테스트 방법 비교

| 방법 | 유형 | 단계 | 장점 |
|------|------|------|------|
| SAST | 화이트박스 | 초기 | 저비용, 넓은 커버리지 |
| DAST | 블랙박스 | SDLC 전반 | 오탐이 적고 런타임 문제 발견 |
| SCA | 의존성 분석 | 빌드 시 | 서드파티 라이브러리 취약점 확인 |

## 3. 무엇이 달라졌나?

### 시프트 레프트(Shift Left) 보안
- "시프트 레프트" 보안(개발 초기 단계에서 보안 확보)이 그 어느 때보다 쉬워짐
- 워크플로에 LLM을 도입해 문제를 발견할 수 있음
- 자동화된 침투 테스트

### 보안 테스트에서의 LLM
- 자동화된 코드 리뷰
- 취약점 탐지
- 수정 제안

## 4. 새로운 AI 에이전트 공격 벡터

| 공격 유형 | 설명 |
|-----------|------|
| **프롬프트 인젝션 (Prompt Injection)** | 숨겨지거나 오해를 유발하는 지시로 AI가 의도된 행동에서 벗어나게 함 |
| **도구 오용 (Tool Misuse)** | 기만적인 프롬프트로 에이전트를 조종해 통합된 도구를 악용하게 함 |
| **의도 파괴 (Intent Breaking)** | 에이전트의 계획을 조작해 원래 의도와 다른 방향으로 행동하게 함 |
| **신원 위장 (Identity Spoofing)** | 탈취된 인증 정보를 악용해 정상 에이전트로 가장 |
| **코드 공격 (Code Attacks)** | 에이전트의 코드 실행 능력을 악용해 실행 환경에 무단 접근 |

## 5. 보안 테스트에서 LLM의 한계

| 한계 | 설명 |
|------|------|
| **높은 오탐률** | Claude Code/Codex의 오탐률은 취약점 유형에 따라 50-100% |
| **비결정적 분석** | 같은 프롬프트를 여러 번 실행하면 결과가 다름 — 모든 취약점을 잡고 있는지 어떻게 알 수 있을까? |
| **컨텍스트 부패 (Context rot)** | 모든 컨텍스트가 똑같이 다뤄지지는 않음 |
| **압축 (Compaction)** | 요약 과정에서 정보 손실 발생 |
| **비현실적인 벤치마크** | 기존 벤치마크는 비현실적인 경우가 많아 LLM 평가가 어려움 |

### 전통적 SAST와의 비교
- AI SAST 오탐률: 50-100% (취약점에 따라 다름)
- 전통적 SAST 오탐률: 50% 이상

| 질문 |
|------|
| 취약점 탐지에서 오탐과 환각을 어떻게 줄일 것인가? |
| LLM이 생성한 패치가 안전하고 회귀(regression)를 일으키지 않는지 어떻게 검증할 것인가? |
| LLM이 왜 취약점으로 판단했는지, 왜 그 수정을 제안하는지 어떻게 설명하게 할 수 있을까? |
| LLM의 애플리케이션 보안(AppSec) 성능을 측정하기 위한 올바른 벤치마크는 무엇인가? |
| 팀이 노이즈에 압도되지 않도록 LLM을 CI/CD에 어떻게 녹여 넣어야 할까? |
| AI가 생성한 패치가 취약점을 만들었다면 책임은 누구에게 있는가? |
