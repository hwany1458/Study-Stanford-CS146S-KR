# 9장: 에이전트 배포와 운영

## 강의 개요

> "프로덕션 환경의 소프트웨어 시스템을 모니터링하는 일은 여전히 핵심 임무다"

코딩은 엔지니어링 시간의 30%에 불과합니다. 더 어려운 나머지 70%는 그 코드를 운영하는 일입니다.

### 학습 목표
- 전통적인 SRE의 책임 이해
- 모니터링의 4대 황금 신호 숙지
- 장애 대응 플레이북 학습
- AI SRE의 특징과 한계 이해

---

## 1. 전통적인 SRE의 책임

| 책임 | 설명 |
|------|------|
| **운영 모니터링** | 온콜, 문제 해결, 인프라 관리 및 보안 |
| **장애 해결** | 여러 출처와 팀의 정보를 짜 맞추는 일 |
| **런북 유지** | 종종 낡아 있는 문제 해결 매뉴얼의 유지 관리 |
| **번아웃** | 온콜 근무로 인한 SRE의 피로 |

### 현대적 과제
- 클라우드 네이티브 아키텍처로의 전환
- 컨테이너화된 워크로드와 Kubernetes
- 시스템 전반에 걸쳐 더 많은 데이터, 의존성, 복잡성이 생겨남

---

## 2. 모니터링의 4대 황금 신호

| 신호 | 설명 |
|------|------|
| **Latency (지연 시간)** | 요청 처리에 걸리는 시간 |
| **Errors (오류)** | 실패한 요청의 비율 |
| **Traffic (트래픽)** | 트래픽 (초당 요청 수) |
| **Saturation (포화도)** | 자원이 얼마나 꽉 차 있는지 |

### 프로덕션 트레이스 모니터링
- 트레이스를 사용해 프로덕션을 모니터링

---

## 3. 장애 대응 플레이북

### 시나리오
> 새벽 3시 12분, PagerDuty에서 데이터베이스 쿼리의 500 오류가 급증하고 있다는 알림이 옵니다. 어떻게 해야 할까요?

### 대응 단계

```
1. 확인 및 평가 (Acknowledge and assess)
2. DB + 앱 점검
3. 최근 변경 사항 파악
4. 영향 범위(blast radius) 국한
5. 완화 조치 실행
6. 안정화 + 모니터링
7. 커뮤니케이션
8. 문서화
```

### 핵심 지표

| 지표 | 설명 |
|------|------|
| **MTTR** | 평균 복구 시간 (Mean-time-to-repair) |
| **온콜 인원 수** | 장애 대응에 투입되는 엔지니어 수 |
| **SLA** | 고객에게 보고하는 서비스 수준 협약 (Service Level Agreement) |

## 5. AI SRE의 특징

> "AI SRE" = 관측 가능성 스택과 여러 클라우드를 아우르는 에이전트 시스템

| 특징 | 설명 |
|------|------|
| **동적 지식 그래프 매핑** | 시스템 구성요소 간 관계를 실시간으로 이해 |
| **관측 스택과 클라우드를 아우르는 에이전트 시스템** | 플랫폼을 넘나드는 지능형 모니터링 |
| **실시간 상황 서술** | 무슨 일이 일어나고 있는지 실시간으로 서술 생성 |
| **근본 원인 분석** | 근거와 함께 가능성 높은 근본 원인을 특정 |
| **수정 권고** | 구체적인 복구 단계 제안 |
| **설명 가능성과 감사 가능성** | 예측/추론에 대한 설명 가능성과 감사 가능성을 크게 강조 |

---

## 6. AI가 무엇을 바꾸었나?

### 지식의 확장
AI는 조직 및 서비스 수준의 지식을 확장해 줄 것으로 기대됩니다.
- 문서화되지 않은 의존성, 깨지기 쉬운 레거시 서비스, 중대한 장애 때만 드러나는 특이한 동작에 관한 정보가 그것을 아는 소수의 엔지니어에게만 갇혀 있지 않게 됨

### 개발 프로세스의 변화
- 자동화가 리뷰 시간을 줄이고 문제를 조기에 발견
- 개발자는 AI 제안을 통해 모범 사례를 학습
- AI는 모든 코드 리뷰에 같은 기준을 적용
- AI가 일상적인 점검을 맡아, 사람은 복잡한 로직에 집중할 수 있음
- AI 시스템은 데이터가 쌓일수록 시간이 지나며 개선됨
- 최신 AI 코드 리뷰 도구는 더 깊이 들어가 문맥 분석과 패턴 인식을 제공

## 7. AI SRE의 한계

| 한계 | 설명 |
|------|------|
| **장애의 복잡도** | 해결할 수 있는 장애의 복잡도에 한계가 있음 |
| **프로덕션 스택의 이질성** | 현대 프로덕션 스택의 다양성 |
| **코드 수정** | 탐지한 내용을 바탕으로 실제 코드를 고치는 능력 |
| **모니터링 가꾸기** | 좋은 근본 원인 분석에는 모니터링의 꾸준한 관리가 필요 |
| **보안 위험** | 새로운 공격 벡터가 될 수 있음 |

### 최종 목표
- 모든 공급자가 근본 원인 분석에서 출발
- 최종 목표는 코드 수정(remediation)
